# 1. ЦЕЛЬ И КОНЦЕПЦИЯ ПРОЕКТА

Разработать единое корпоративное веб-приложение Marking ERP, объединяющее процессы работы с Национальным каталогом, эмиссии и нанесения кодов маркировки, формирования агрегированных таможенных кодов (АТК), складской приёмки и отгрузки, разделения КМ, логистики и контроля операций в системе «Честный знак».

Новая ERP должна заменить четыре ранее созданных самостоятельных приложения.

**Принципиальное требование: создать единый продукт, а не объединить четыре независимых сайта общей навигацией.**

Все модули должны использовать:

- Единую PostgreSQL.
- Общий справочник организаций.
- Общий товарный каталог, синхронизируемый с боевым Национальным каталогом.
- Единый реестр КМ.
- Общие документы и связи между ними.
- Централизованную авторизацию.
- Шесть групп пользователей.
- Настраиваемую матрицу прав доступа.
- Настраиваемые бизнес-правила.
- Общий механизм интеграций с ЦРПТ.
- Единую очередь внешних операций.
- Общий Windows-подписант.
- Единую дизайн-систему и пользовательский интерфейс.
- Централизованный журнал событий и ошибок.

**Главная бизнес-цель:** исключить повторный ввод данных и передачу Excel между внутренними модулями ERP.

Основной сквозной процесс:

**Национальный каталог → БМ → Логист → Склад → завершение логистических операций.**

Отдельные связанные процессы:

- Складская отгрузка.
- Проверка КМ.
- Разделение КМ.
- Перепечать этикеток.
- Восстановление повреждённой маркировки.
- Ввод импортированных товаров в оборот с ФТС.
- Контроль ошибок и проблемных операций.

## 2.1. Обязательные условия

1. Исходные репозитории не изменять.
2. Создать новый репозиторий `marking-erp`.
3. Не переносить существующие базы данных.
4. Не переносить старые тестовые документы и КМ.
5. Начать с новой чистой PostgreSQL.
6. Не требовать обратной совместимости со старыми схемами SQLite.
7. Переиспользовать работающий код, если он прошёл аудит.
8. Не переносить известные ошибки и технический долг без обоснования.
9. Не переписывать работающую функциональность без необходимости.
10. Не выполнять платные или юридически значимые операции в продуктивном ЧЗ без разрешения владельца.

## 2.2. Особое условие для nk-manager

`nk-manager` продолжает активно дорабатываться.

Агент вправе изучать его во время предварительного аудита, но окончательный перенос должен выполняться из актуального состояния `main`.

Перед переносом:

- Повторно получить исходники.
- Зафиксировать SHA.
- Проверить изменения после первоначального аудита.
- Проверить новые функции и тесты.
- Перенести актуальную реализацию.
- Не изменять исходный `nk-manager`.

Для остальных репозиториев также фиксировать SHA исследованных версий.

## 2.3. Отказ от миграции

Старые операции и локальные данные не требуются.

Это позволяет свободно спроектировать новую модель данных, избавиться от дублирующихся сущностей и отказаться от промежуточных адаптеров между четырьмя SQLite.

При этом сохранять защиту от повторного выполнения внешних операций.

Удаление локальных тестовых данных не означает удаления объектов, которые могли существовать в реальных системах ЦРПТ.

# 5. ШЕСТЬ ГРУПП ПОЛЬЗОВАТЕЛЕЙ

Реализовать шесть предустановленных системных групп.

**Список групп является обязательным:**

1. **БМ**
2. **Логист**
3. **Склад**
4. **ТСД**
5. **Специалист по маркировке**
6. **Администратор**

Группы должны существовать после первоначального развёртывания.

Группы имеют настраиваемые permissions.

В первой версии пользователь принадлежит одной основной группе.

## 5.1. БМ

БМ работает преимущественно со своими накладными и карточками товаров.

Основные права:

- Просмотр НК.
- Создание и редактирование карточек.
- Проверка дублей.
- Получение GTIN.
- Публикация.
- Создание и импорт накладных.
- Эмиссия КМ.
- Работа с этикетками.
- Отчёты о нанесении.
- Формирование АТК.
- Подготовка допустимых трансформаций.
- Просмотр своих документов.
- Остановка собственных накладных.

Не имеет доступа к системным настройкам.

## 5.2. Логист

Основные права:

- Общий реестр готовых АТК.
- Просмотр сведений по накладным.
- Скачивание АТК и RESULT.
- Передача накладных на склад.
- Просмотр складской приёмки.
- Работа с расхождениями.
- Операции ФТС.
- Закрытие готовых накладных.
- Архивирование по правилам процесса.

## 5.3. Склад

Основные права:

- Складская приёмка.
- Складская отгрузка.
- Одиночная и пакетная проверка КМ.
- Разделение КМ.
- Перепечать допустимых этикеток.
- Просмотр собственных складских документов.
- Регистрация расхождений.
- Работа с проблемными складскими операциями.

## 5.4. ТСД

**Специализированная ограниченная группа.**

Пользователю группы «ТСД» доступны исключительно:

1. **Приёмка.**
2. **Проверка КМ.**
3. **Отгрузка.**

Внутри этих разделов доступны необходимые действия сканирования, проверки и завершения разрешённых складских документов.

Недоступны:

- Национальный каталог.
- Работа БМ.
- Логистика.
- АТК.
- Разделение КМ.
- Перепечать этикеток.
- Создание произвольных документов и Excel-импорт.
- Общий реестр КМ.
- Общий архив.
- Управление пользователями.
- Бизнес-правила.
- Настройки.
- Интеграции.
- Административные журналы.

**Не создавать отдельный backend для ТСД.**

Использовать те же складские API и проверки, что и в полноценном интерфейсе группы «Склад».

Группа «ТСД» определяет полномочия, а не тип физического устройства.

Пользователь ТСД на ПК также видит только три раздела. Пользователь группы «Склад» на Android сохраняет свои права.

## 5.5. Специалист по маркировке

**Полная операционная суперроль.**

Имеет доступ ко всем бизнес-операциям всех модулей:

- НК.
- БМ.
- Эмиссия.
- Нанесение.
- АТК.
- Трансформации.
- Логистика.
- Склад.
- ТСД-сценарии.
- Разделение.
- Перепечать.
- Перемаркировка, если реализована.
- ФТС.
- Архив.
- Восстановление документов.
- Операционная диагностика.
- Разбор ошибок.

**Исключения:**

- Управление пользователями.
- Изменение групп.
- Изменение прав доступа.
- Настройка бизнес-логики.
- Управление подключениями и секретами.
- Административная конфигурация системы.

## 5.6. Администратор

**Все права без исключения в пределах технически и юридически допустимых операций.**

Может управлять пользователями, группами, правами, настройками, интеграциями, документами и бизнес-правилами.

Не может отключить обязательные инварианты безопасности и требования внешних API.

Одиночная проверка через True API.

1. Пользователь сканирует КМ.

3. Показывает бизнес-результат.

# 14. ПЕРЕДАЧА ЛОГИСТОМ В СКЛАДСКУЮ ПРИЁМКУ

**Критически важный новый бизнес-процесс.**

Существующий `gis-trueapi` уже содержит работающий модуль приёмки.

Его необходимо переиспользовать.

**Изменить основной источник создания документа: вместо ручного Excel данные поступают напрямую от логиста.**

## 14.1. Начало процесса

После готовности АТК и подтверждения необходимых операций у логиста появляется кнопка:

**«Передать в приёмку»**

При нажатии ERP создаёт складское задание.

## 14.2. Содержимое задания

Складское задание содержит:

- ID исходной накладной.
- Номер и дату.
- Поставщика.
- Нашу организацию.
- БМ.
- Логиста.
- PN.
- GTIN.
- Количество.
- Полный список ожидаемых КМ.
- Полные DataMatrix.
- Количество в каждом КМ.
- Связанные АТК.
- Версию подтверждённого состава.
- Дату передачи.

Не создавать промежуточный Excel.

Не выполнять новую эмиссию.

## 14.3. Несколько накладных

Если один АТК объединяет КМ нескольких накладных, создавать отдельное складское задание для каждой исходной накладной.

Не переносить все КМ общего АТК в каждое задание.

Использовать происхождение КМ и подтверждённые трансформации.

Выполнить контроль отсутствия дублирования кодов между несовместимыми активными складскими заданиями.

## 14.4. Повторная передача

Операция должна быть идемпотентной.

Повторное нажатие открывает существующее задание.

Не создаёт дубликат.

## 14.5. Изменение состава

Если после передачи изменился состав КМ:

- Обнаружить несоответствие ревизий.
- Не обновлять ожидания склада молча.
- Заблокировать проверку по устаревшему составу.
- Уведомить сотрудников.
- Требовать явного обновления или замены задания.
- Сохранить историю предыдущей версии.

## 14.6. Результат

После проверки склада логист видит:

- Ожидалось.
- Отсканировано.
- Принято.
- Отсутствует.
- Лишних.
- Проблемных.
- Статус проверки.
- Статус завершения.

## 14.7. Закрытие накладной

Передача на склад не завершает накладную.

Закрытие допускается после выполнения обязательных этапов логистики и успешной приёмки, если она требуется по процессу.

# 15. СКЛАДСКАЯ ПРИЁМКА

Переиспользовать существующую функциональность `gis-trueapi`.

## 15.1. Процесс

1. Склад получает задание от логиста.
2. Сотрудник открывает документ.
3. Начинает сканирование.
4. ERP сохраняет каждый скан.
5. Сотрудник нажимает «Проверить».
6. Выполняется локальная сверка с ожидаемыми полными КМ.
7. Система показывает результат.
8. При отсутствии ошибок сотрудник завершает приёмку.
9. Результат передаётся логисту.

## 15.2. Проверки

- Полное совпадение КМ.
- Совпадение криптографической части.
- Отсутствие дублей.
- Правильный GTIN.
- Правильное количество.
- Полнота ожидаемого набора.
- Отсутствие лишних кодов.

Не ограничиваться совпадением количества.

## 15.3. Расхождения

Поддерживать:

- Лишний КМ.
- Отсутствующий КМ.
- Дубликат.
- Несовпадающий DataMatrix.
- Неверный GTIN.
- Ошибку количества.

Сохранять существующую механику регистрации расхождений, адаптировав её к единому реестру.

## 15.4. Совместная работа

Документ может быть начат на ПК и продолжен на ТСД.

Сканы сохраняются в общей PostgreSQL.

Контроль ревизий исключает потерю параллельных изменений.

## 15.5. Excel

Ручную загрузку Excel оставить дополнительным резервным способом создания складского документа по отдельному разрешению.

Для основного процесса БМ → Логист → Склад Excel не используется.

# 16. СКЛАДСКАЯ ОТГРУЗКА

Сохранить существующие возможности `gis-trueapi`.

Процесс:

1. Открытие документа.
2. Сканирование.
3. Немедленная локальная проверка GTIN по ожидаемому списку.
4. Сохранение сканов.
5. Нажатие «Проверить».
6. Пакетная проверка через True API.
7. Проверка владельца, статуса и количества.
8. Завершение при отсутствии ошибок.
9. Формирование итогового файла КМ.

Не обращаться к True API при каждом скане.

Обязательно учитывать `quantityInPack`.

Не считать количество сканирований количеством товара.

# 17. РАЗДЕЛЕНИЕ КМ

4. Определение доступного остатка.

12. Подтверждение квитанции.
13. Обновление истории.

Не допускать двойного расходования остатка.

Повторная печать PDF не должна выполнять новую эмиссию.

# 18. ПЕРЕПЕЧАТЬ И ВОССТАНОВЛЕНИЕ ЭТИКЕТОК

## 18.1. Перепечать сохранённой этикетки

6. Печатает.
7. Выполняет контрольное сканирование, если оно требуется правилом.

Не создавать новый отчёт о нанесении.

## 18.2. Официальная перемаркировка

Предусмотреть архитектуру:

- Проверка исходного КМ.

- Новый КМ, если он необходим.
- Подписание.
- Документ перемаркировки.
- Подтверждение результата.
- История старого и нового КМ.

До подтверждения официального API и бизнес-процесса не реализовывать изменяющие запросы по предположению.

## 18.3. Печать

Поддержать:

# 28. ОБЯЗАТЕЛЬНЫЕ СКВОЗНЫЕ СЦЕНАРИИ

## A. Национальный каталог → БМ

Карточка создаётся или актуализируется в НК, GTIN подтверждается, товар становится доступен БМ.

## B. БМ → нанесение → АТК

Накладная проходит эмиссию, печать, подтверждение нанесения, отчёт, АТК и итоговые файлы.

## C. БМ → Логист → Склад

Логист получает готовую накладную и передаёт в приёмку одним действием.

Склад автоматически получает ожидаемые КМ.

Excel не требуется.

## D. Складская приёмка на ПК и ТСД

Два устройства могут последовательно или одновременно работать с одним документом.

Проверяются полные КМ.

Результат передаётся логисту.

## E. Складская отгрузка

Сканирование, немедленная проверка GTIN, пакетная проверка True API, завершение.

## F. Разделение КМ

Исходный КМ проверяется, количество резервируется, новый КМ эмитируется, отчёт подтверждается.

## G. Перепечать

Повторная печать сохранённого полного КМ не вызывает новую эмиссию.

## H. Изменение прав

Администратор изменяет permission группы.

Доступ к UI и API обновляется без перезапуска.

## I. Изменение бизнес-правила

Администратор меняет допустимое правило.

Новые операции используют новую версию.

Исторические операции остаются неизменными.

## J. Группа ТСД

Пользователь группы ТСД видит только:

- Приёмка.
- Проверка КМ.
- Отгрузка.

Прямые API-запросы к остальным модулям возвращают отказ.

## K. Специалист по маркировке

Специалист выполняет все операционные сценарии, но не может изменять права, пользователей и настройки.

# 34. ИТОГОВОЕ ОПРЕДЕЛЕНИЕ ГОТОВОГО ПРОДУКТА

Marking ERP представляет собой единую корпоративную систему, в которой:

**БМ** управляет номенклатурой, эмиссией, нанесением и АТК.

**Логист** получает готовые документы, передаёт груз в приёмку, контролирует результаты и выполняет логистические операции.

**Склад** принимает и отгружает товар, проверяет КМ, выполняет разделение и допустимую перепечать этикеток.

**ТСД** предоставляет только три простых действия: приёмку, проверку КМ и отгрузку.

**Специалист по маркировке** имеет все операционные возможности ERP и решает сложные вопросы маркировки.

**Администратор** управляет всеми процессами, пользователями, правами, настройками и интеграциями.

Все сотрудники используют общую систему.

Все модули работают с едиными товарами, КМ и документами.

Внутренний обмен Excel между модулями не требуется.

Все внешние операции с ЧЗ выполняются по проверенной бизнес-логике и актуальным API-контрактам.

**Итоговый критерий успеха: безопасная, удобная, управляемая и единая Marking ERP, готовая к работе в корпоративной инфраструктуре после прохождения необходимых интеграционных испытаний.**
