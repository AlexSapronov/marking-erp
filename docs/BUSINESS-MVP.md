# Бизнес-модули ERP — реализация и границы проверки

27.10.2026. Это описание кода, не акт успешного боевого пилота.

## Источники переноса

- marking-bm: `6a55adb9b6ce50872141416322fd10bc8d790a45`.
- nk-manager: `36efc06a38ec4e06fd6fcc21307bc397f9258135`.
- km-split: `19c8329a2f9c4298853939c7d68a91443cf98bf3`.
- gis-trueapi: обновлённый main от 26.10.2026; источник складских правил статусов.

Перенесены контракты исходных приложений. Код работает через PostgreSQL, общие
учётные записи, права, историю и durable operations. Отдельные SQLite-приложения,
iframe и демонстрационная эмиссия не используются.

## Подключение после установки

Обновить сервер по DEPLOY-VPS.md: backup → остановка → новый релиз → migrate →
grant-runtime → запуск. Схема: **0013_official_flows**. Служба сама не выполняет миграции.
`signer_verifiers` доступна runtime-роли только на чтение. Новые истории и артефакты
не изменяются задним числом; PDF/XLSX хранятся внутри БД и входят в pg_dump.

В администраторском разделе **«Подключения»** после свежего MFA указать организацию,
контур, OMS ID/соединение, шаблон 36/37, API KEY НК и действующие токены ЧЗ/СУЗ.
Секреты шифруются постоянным MFA-ключом сервера; API их не возвращает. Пустое поле
сохраняет прежний секрет. Автообновление токенов по challenge доступно через доверенный Windows-подписант; настройка описана в LABEL-AND-OFFICIAL-FLOWS.md.

Для проверки склада включить соответствующую настройку. Если разрешено игнорировать
юридическое лицо, проверка установленного владельца всё равно выполняется, но его
ИНН не сравнивается с ИНН организации. Такое послабление выбирает администратор явно.

Отправка выключена до явного включения администратором. В режиме НК sandbox
адаптеры ЧЗ/СУЗ отклоняют запросы: их тестовые адреса требуют отдельного подтверждения.

## Windows-подписант

Включить профиль внешних операций через сохранение подключений, затем на сервере
под maintenance-ролью зарегистрировать устройство. SHA256 — отпечаток DER-сертификата,
не SHA1 thumbprint, который использует Windows для поиска сертификата:

```bash
sudo /opt/marking-erp/current/venv/bin/marking-erp-admin register-signer \
  --organization-id UUID_ОРГАНИЗАЦИИ --name 'Рабочий подписант' \
  --certificate-sha256 SHA256_СЕРТИФИКАТА \
  --kind nk.publish --kind bm.order --kind bm.report --kind bm.atk \
  --kind bm.transform --kind split.order --kind split.report
```

Команда выводит Device ID и отдельный bearer-токен один раз. Сохранить приватно,
не в Git, чате или письме. Верификация на этом Windows-ПК — отдельная доверенная роль;
её разрешает только администратор сервера:

```bash
sudo /opt/marking-erp/current/venv/bin/marking-erp-admin trust-windows-verifier \
  --device-id UUID_УСТРОЙСТВА
```

Эта команда означает доверие проверке CryptoPro на указанном ПК. Обычная CMS,
полученная без такого доверия, остаётся `received_unverified`. Браузерные сессии
не могут подтвердить криптографическую проверку.

Скопировать `deploy/windows/Start-ErpSigner.ps1` и `Sign-Payload.vbs` на Windows.
CryptoPro/CAdES и Рутокен должны быть настроены в текущем профиле. В PowerShell:

```powershell
.\Start-ErpSigner.ps1 -BaseUrl "https://erp.company.ru" -Thumbprint "SHA1_ОТПЕЧАТОК"
```

Токен вводится скрыто. При необходимости 32-битного COM добавить `-Use32Bit`.
Права администратора Windows скрипту не нужны. Проверяются точные байты payload,
закреплённый сертификат, подпись и цепочка через CryptoPro. Полученная проверка
передаётся от отдельно зарегистрированного доверенного устройства и привязана к
job/fence/SHA256. Доверие такому ПК и сохранность его bearer-токена — часть границы
безопасности. Реальный запуск на Windows и проверка CRL/цепочки **ещё не выполнены**.

## Ошибки и восстановление

- `unknown`: не выдавать новую команду с новым ключом. Сначала сверка с ЛК/оператором.
- `submitted`: сервер повторяет чтение статуса, не отправку документа.
- `before_dispatch:*`: consuming-запрос не выполнен; после устранения причины
  можно явно возобновить проверку. Другие blocked/unknown не переотправляются этой кнопкой.
- Архив останавливает ожидающие команды, сохраняет отправленные результаты и квитанции.
  Восстановление не переотправляет отменённые команды автоматически.
- Отключение пользователя/права/устройства проверяется повторно перед отправкой.
- Изменение роли и закрытие документа сохраняют исключительную глобальную координацию.
  Сканирование разных складских заданий использует shared-fence и отдельные row locks.

## Приёмка

Исправления ревью отдельно приняты в PR #21, включая реальный PostgreSQL16/Chromium,
offline installer, systemd, HTTPS и restore. Это **не** подтверждает новый бизнес-срез.
Для него локально выполнены синтаксические проверки, генерация SQL миграций,
CRUD карточек/дублей/шаблонов/Excel/шифрованных настроек и накладная → очередь эмиссии
на временной PGlite-базе. Полные тесты нового среза и внешний пилот указываются
отдельно в PR; PGlite не заменяет PostgreSQL16.

Ни реальные КМ, ни успешная эмиссия, ни подпись, ни результаты ЧЗ в локальной проверке
не имитировались. До реальной приёмки с НК/СУЗ/ЧЗ, Windows и S55/S45 нельзя считать
перенос всех четырёх приложений завершённым или заменять ими рабочий контур.


## Единый реестр КМ (0009_code_registry)

Получение КМ для маркировки и разделения сохраняет общий КИ, неизменяемые
байты, источник и автора в реестре `/codes`. Подтверждённое перераспределение
AI30 добавляет событие «Перераспределение количества»; криптохвост не меняется.
Реестр показывает последнее принятое количество, а конфликтное наблюдение не
замещает его. Отдельный PDF в истории — точная копия PDF из ZIP процесса.
После перераспределения и возврата в пул прежний PDF недоступен для скачивания.
Склад видит коды назначенных накладных; отмена задания отзывает этот доступ.

При обновлении с 0008 сначала выполнить миграцию и `grant-runtime`.
Для уже полученных в этой ERP бизнес-КМ предусмотрена локальная команда:

```bash
sudo /opt/marking-erp/current/venv/bin/marking-erp-admin sync-code-registry --actor-id UUID_АДМИНИСТРАТОРА
```

Команда переносит коды только организаций действующего администратора,
копирует существующие PDF без перерисовки, повторный запуск безопасен.
Свободные КМ без текущей накладной регистрируются при следующем резервировании.
Внешние запросы и эмиссия при переносе не выполняются. История старых SQLite
приложений не импортируется. При конфликте байтов перенос останавливается;
противоречивые данные не заменяются.


## Завершение накладной логистом и партии поставщика

В «Логистике» кнопка «Закрытие накладных» открывает документы в работе и
завершённые. «Проверить этапы» показывает причины, мешающие закрытию.
Для текущего импортного процесса требуются:

- Подтверждённый отчёт о нанесении всех ожидаемых КМ.
- Полный состав КМ в зарегистрированных АТК, отмеченных как переданные поставщику.
- Реальное подтверждение ФТС (документ ЧЗ + проверка INTRODUCED).
- Приёмка, если её требует снимок правил исходной накладной.
- Все созданные складские задания закрыты по актуальной версии и проверены в ЧЗ.
- Нет незавершённых трансформаций или неразобранных операций.

Физическая сверка без проверки ЧЗ и подготовленное досье ФТС не считаются
подтверждением этих этапов. При закрытии сотрудник вводит номер накладной;
сохраняются автор, время и использованные доказательства. Повтор запроса
после сетевого сбоя безопасен. Возврат в работу требует права documents.restore,
номера и причины. До возврата нельзя менять складское задание или архивировать
связанные АТК/ФТС. История завершения остаётся в аудите.

В форме АТК выбирается поставщик. Партия включает все его активные накладные,
ещё не включённые в АТК, включая документы за пределами первой страницы реестра.
Незавершённый отчёт любой накладной блокирует партию; другие поставщики независимы.
Ненужные накладные исключаются явным архивированием. Если партия содержит чужие
накладные, формирование выполняет специалист с полномочиями по всей партии.
Названия поставщиков учитывают административный справочник алиасов; исходные наименования в версиях сохраняются.
Excel АТК содержит только КМ своего полного ТН ВЭД и получает новую версию после
успешной трансформации. Ранее сохранённые версии остаются в истории.


## Большие каталоги и ошибки отчётов (0010_catalog_sync)

Перенесён алгоритм разбиения временных окон из nk-manager
`36efc06a38ec4e06fd6fcc21307bc397f9258135` (`sync_tick`). Общие границы
интервалов перекрываются; таблица catalog_sync_entries считает good_id ровно
один раз. Страницы и прогресс сохраняются атомарно. Перезапуск worker продолжает
сохранённое окно. HTTP 429 сохраняет прогресс, неизвестный или неполный ответ
останавливает синхронизацию без ложного завершения. Старые задания без окон
после обновления начинают безопасный повтор читающей синхронизации с начала.

В НК кнопка «Ход синхронизации» показывает число уникальных карточек,
оставшиеся интервалы, причину остановки и продолжение после исправления.
Экспорт учитывает текущий фильтр и не обрезает файл молча по 10000 строкам:
лимит — 50000, при превышении требуется уточнить фильтр.

Отклонение отчёта с известным сообщением об отсутствующей карточке/правах
отображается сотруднику как неготовая или недоступная карточка НК с предложением
повторить позже либо обратиться к ответственному. Исходная квитанция хранится
отдельно. Кнопка повторной отправки доступна только при отклонении именно отчёта,
а не заказа эмиссии. Неизвестная отправка автоматически не повторяется.
После миграции необходимо обновить runtime grants; новая таблица прогресса
защищена от изменения и удаления истории. Реальные токены и платные операции
этими проверками не использовались.


## Возврат в БМ для полного состава поставки (0011_suppliers)

Основная цепочка: исходная маркируемая часть БМ → эмиссия → нанесение →
подтверждённый отчёт → АТК → логист подтверждает передачу поставщику →
**«Вернуть в БМ для полного Excel»** → БМ/закупщик дополняет полный состав →
логист передаёт на склад → приёмка/отгрузка → завершение логистики.

Первоначальный документ БМ содержит только маркируемые строки. Немаркируемые
товары добавляются на отдельном этапе после возврата, а не выдаются за часть
заказа КМ. В реестре БМ появляется статус «Дополнить состав для склада».
Доступен шаблон с уже промаркированными PN/GTIN и общими количествами;
к нему добавляются остальные позиции. Либо загружается полный Excel поставки
с сопоставлением PN, GTIN и общего количества.

Сервер сверяет все маркированные PN/GTIN и суммы количеств с исходным
документом. Изменить их, пропустить или перенести известный PN в строки без
GTIN нельзя. Новые строки без GTIN сохраняются как немаркируемые; повторные
строки сохраняются отдельно. Предпросмотр не изменяет документ. При сохранении
повторно проверяются ревизии, права, фаза процесса и SHA256 файла.

Сохраняются оригинальный XLSX, новая версия состава, автор и время. Старые
payload КМ, этикетки, отчёты и АТК остаются неизменными; новой эмиссии нет.
Маркированные строки сохраняют порядок и индексы. Пока полный состав не готов,
документ после маркировки нельзя передать на склад. Для исправления полного
состава логист возвращает его БМ повторно, предварительно отменив старые задания.

Склад показывает немаркируемые строки по отдельному переключателю. Они
информационные: не входят в план сканов КМ и не считаются подтверждёнными
сканированием других товаров. Экспорт отгрузки сохраняет их на отдельном листе
с явной пометкой; общее количество товара не заменяется числом КМ.

В «Подключениях» администратор открывает «Поставщики и алиасы». Объединение
и отделение написаний требуют причины, свежей административной авторизации
и актуальной ревизии справочника. Партии АТК, выбор для трансформации и поиск
накладных учитывают единое имя. Исходные названия, версии накладных и подписанные
данные не переписываются. Объединение, создающее дубли накладных одного владельца
с одинаковыми номером и датой, блокируется до разбора дублей.

## Рабочий список НК: опубликованный PN и черновики

По умолчанию реестр скрывает черновики, если у доступной сотруднику карточки уже
есть **точно такой PN в подтверждённом опубликованном ответе НК**. Символы, регистр,
дефисы и косые черты не нормализуются для скрытия. Похожий PN по-прежнему может
вызвать предупреждение при создании, но не является основанием скрыть карточку.

Фильтр «Совпадения с опубликованными»: скрыть такие черновики, показать все либо
показать только их. В последнем случае строки отмечены «PN уже опубликован».
Фильтр применяется до пагинации и к Excel; выгрузка учитывает поиск и архив.
При смене фильтра выбор для массовых действий сбрасывается.

Опубликованные карточки, карточки на модерации и ожидающие подписи остаются видны.
Если опубликованная карточка локально отредактирована, для сравнения используется
PN из сохранённого внешнего ответа, а не ещё не подтверждённая правка. При
неоднозначном PN в ответе НК программа не выбирает один из вариантов для скрытия.
Локальный архив не отменяет опубликованный статус в НК; сам архив отображается
полностью с учётом поиска. Недоступная сотруднику опубликованная карточка не
изменяет его список и не раскрывается через признак совпадения.

Скрытие — только представление реестра: черновик доступен по фильтру и прямой
ссылке при наличии прав. Данные не удаляются и не архивируются, синхронизация и
история продолжаются, повторное создание не запускается. Новая миграция не нужна.
