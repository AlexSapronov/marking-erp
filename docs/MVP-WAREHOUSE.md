# Складской MVP в единой ERP

Реальный сохраняемый бизнес-процесс: подготовка накладной БМ → передача логистом →
назначенное задание приёмки/отгрузки → сканирование упаковок → полная физическая
сверка → закрытие. Данные сохраняются в PostgreSQL, участники работают под своими
учётными записями. Новые тесты и полный CI отложены по поручению пользователя.

## Что показать руководству

1. **БМ / «Накладные БМ».** Создать накладную вручную либо через существующий
   Excel-импорт. Для каждой строки указать PN, GTIN, полный ТН ВЭД, количество штук
   в упаковке и число этикеток. Сохранить и нажать «Проверить состав».
2. **Логист / «Логистика».** Нажать «Передать на склад», выбрать проверенную
   накладную, приёмку или отгрузку и конкретных сотрудников склада/ТСД. Накладная
   появляется среди последних 200 проверенных документов. Для одной накладной
   возможно по одному действующему заданию каждого типа. Назначения проверяются
   по организации и действующему праву сканирования.
3. **Склад / ТСД / «Приёмка» или «Отгрузка».** Открыть назначенное задание.
   Видны план, факт и остаток по КМ и штукам. По умолчанию завершённые скрыты.
   Доступны поиск по номеру/поставщику и постраничный список.
4. Сканировать полные Data Matrix с сохранением GS-разделителей. GTIN проверяется
   сразу. Количество берётся из AI30, при его отсутствии — одна штука. Программа
   отклоняет чужой GTIN, неправильное количество, повторный КМ и превышение плана.
   Если GTIN и фасовка соответствуют нескольким PN, сотрудник выбирает строку PN.
5. Показать отказ повторного скана. При ошибке сотрудник удаляет нужный скан
   из последних 100 записей и сканирует верный код. Удаление сохраняется в истории.
6. После полного совпадения плана и факта ввести номер накладной и закрыть задание.
   При недостающих КМ закрытие запрещено. Для отгрузки становится доступна итоговая
   Excel-выгрузка с PN, GTIN, количеством, КМ, сотрудником и временем сканирования.
7. **Логист.** Обновить список и открыть результат. Видны общий прогресс, строки,
   последние сканы и история. При необходимости открытое задание можно отменить
   с указанием причины и номера накладной, затем создать новое.

Для приёмки и отгрузки используются одинаковые механизмы, отдельные назначения,
сканы и состояния. После успешной приёмки отгрузка не создаётся автоматически.

## Правила работы

- Сотрудник видит только задания своей организации и разрешённой области
  (`all`, `own`, `assigned`). ТСД и склад по умолчанию имеют область `assigned`.
- Действующее или закрытое складское задание фиксирует состав исходной накладной.
  Для изменения состава сначала нужно отменить открытые задания. Закрытое задание
  сначала возвращает в работу специалист/администратор с правом `warehouse.documents.reopen`.
- Архивирование исходной накладной останавливает дальнейшие сканы. Отмена задания
  логистом доступна и при архивной исходной накладной. Возврат исходной накладной
  при сохранившихся заданиях потребует их предварительной отмены.
- Изменения защищены CSRF и проверкой прав при каждом запросе. Перекрытие действий
  сериализуется существующей транзакционной блокировкой приложения. Повторы передачи
  и скана с тем же request_id не создают повторных данных.
- Экспорт содержит только активные сканы полностью закрытой отгрузки. GS представлен
  как `<GS>` — это файл сверки, не готовый документ для отправки в ЧЗ/ЭДО.
- Проверяется соответствие GTIN и количества ожидаемому составу. Ожидаемый перечень
  конкретных серийных КМ в этом срезе не импортируется.
- Поддерживается существующий строгий парсер радиоэлектроники, шаблоны 36/37.
  AIM-префикс `]d2` и завершающий Enter обрабатываются; потерянные GS не угадываются.
- При сетевой ошибке поле скана сохраняется. Повторяется тот же request_id.
  Следующий код сканировать после сообщения о принятии предыдущего. Офлайн-очереди нет.
- В историю записываются передача, принятие/удаление скана, закрытие, возврат,
  отмена и выгрузка. Сырые КМ не выводятся в общий журнал аудита.

## Обновление VPS

Этот функционал отсутствует в старом пакете PR #19. Для установки нужен новый
пакет коммита с данной доработкой. Базовый порядок — раздел обновления в
[DEPLOY-VPS.md](DEPLOY-VPS.md): резервная копия, остановка сервиса, установка нового
релиза, миграция, повторная выдача runtime-прав, переключение `current`, запуск.

Схема: **0007_warehouse**. После миграции обязательно выполнить существующую
команду `grant-runtime` из maintenance-конфигурации: добавлены `warehouse_tasks`,
`warehouse_scans`, `warehouse_events` и sequence событий. Сервис сам не мигрирует БД.
Не откатывать схему с удалением складских таблиц после начала реальной работы.

Ни демонстрационные пользователи, ни тестовые КМ автоматически не создаются.
Для показа на рабочем контуре использовать согласованную накладную и реальные
этикетки. Сотрудников и группы создаёт администратор обычным способом.

## Границы готовности

Это физическая складская сверка. Она не подтверждает статус КМ, владельца,
проверку криптографии, ввод в оборот или передачу прав в ЧЗ. Эмиссия, нанесение,
АТК, ФТС, НК и split сохраняют ограничения из [DELIVERY-STATUS.md](DELIVERY-STATUS.md).
Внешние продуктивные операции и Windows-подписант данным изменением не включаются.

Проверка в этой среде: компиляция Python, синтаксис JS, генерация SQL миграций,
локальный проход бизнес-процесса и просмотр UI на временной PGlite-базе.
PGlite не заменяет целевую PostgreSQL16 и не подтверждает готовность оборудования.
Полный набор тестов, проверка целевой runtime-роли, нагрузка и сканер отложены.
