## Реализованный срез

`nk_read_contract.py` проверяет только envelope, пагинацию и состав good_id.
Это **проектная политика принятия свидетельств ERP**, не полный валидатор карточки НК:

- Явный неизменяемый временной интервал, без угадывания часового пояса.
- Страницы до25, чтобы детали укладывались в один запрос; последний limit сокращается.
- Для доказательства охвата обязательны total и совпадающие offset/limit. Отсутствие
  допустимого необязательного поля означает недостаточность свидетельств, не нарушение API НК.
- Строгие JSON-типы, уникальные положительные good_id, точный состав деталей,
  отсутствие пропусков/повторов между страницами, постоянный total.
- Пустая выборка принимается только при явном total=0. При ошибке состояние предыдущей
  проверки неизменно; внешние запросы и автоматические повторы отсутствуют.
- SHA256 считается по исходным байтам каждого тела ответа, неизвестные поля не переписываются.
  Hash доказывает тождество файла, но не происхождение или подлинность ответа.

Результат `bounded_pass` означает только согласованный обход заданной выборки.
Даже при постоянном total возможна перестановка удалённых карточек с пропусками:
на основании такого результата нельзя удалять локальные карточки, подтверждать PN,
публикацию, принадлежность организации или присваивать `nk_confirmed`.
Результат всегда содержит atomic_snapshot=false, authenticity_verified=false, erp_imported=false.
Конструктор проверок не подключён к веб-приложению, очереди или БД.

## Офлайн-проверка записанных ответов

После установки проекта: `marking-erp-nk-check --manifest /private/pilot/manifest.json`.
Без установки entrypoint: `python -m marking_erp.nk_read_cli --manifest ...`.
HTTP200 тела сохраняются отдельно исходными байтами; статус/среду/учётную запись
оператор фиксирует в закрытом протоколе пилота. Утилита сама их не удостоверяет.
Не помещать API KEY, URL с ключом или заголовки Authorization в manifest/репозиторий.

```json
{
  "format": 1,
  "window": {"from_date": "2026-10-01 00:00:00", "to_date": "2026-10-25 00:00:00"},
  "page_size": 25,
  "pages": [
    {"offset": 0, "limit": 25, "listing": "list-0.json", "details": "details-0.json"}
  ]
}
```

listing — полный JSON envelope apiversion4 с result.total/offset/limit/goods;
details — envelope apiversion3 с result-массивом карточек. При пустой выборке details=null.
Файлы лежат рядом с manifest; вложенные пути и symlink файлов запрещены.
Размер каждого файла ограничен8MiB, JSON с повторными ключами отклоняется.
Запуск печатает только счётчики, признаки ограничений и hash тел, не содержимое карточек.
Коды завершения:0 — bounded_pass;2 — неполный обход;1 — ошибка свидетельств.
Утилита не делает сетевых обращений и не меняет файлы или данные ERP.

## Что ещё требуется

Все записи полного контракта в API-COMPLIANCE остаются UNVERIFIED.
Синтетические регрессии не закрывают I-001 и CHECKPOINT.
Перед адаптером нужны закрытые реальные образцы и контролируемый read-пилот:
права владельца/субаккаунта, пустые и многостраничные выборки, изменяющийся состав,
границы времени и одинаковые секунды,413/429/Retry-After,403/404 деталей,
неизвестные статусы и обязательность/nullable полей карточки. Политика413 требует
отдельного решения по пересекающимся границам; автоматического дробления здесь нет.
Транспорт с защитой секретов, квотами и ограниченными повторами пока не подключён.
Расходующие GET generate-gtins/feed-moderation не входят в этот читающий срез.
