# Редактор групп и внутренней политики

После `marking-erp migrate` до `0003_policy` доступны `/groups` и `/rules`. Шесть групп фиксированы. Для входа в разделы нужны соответственно permissions.manage или business_rules.manage и подтверждённый за последние пять минут административный доступ. API всегда проверяет эти условия, cookie/Origin/CSRF остаются обязательными.

## Группы и права

Поиск и фильтр модулей, описание, тип действия, области «свои/назначенные/все/запрет», зависимости чтений. Массовые действия применяются только к найденным строкам; базовый профиль восстанавливается в черновике. Изменения требуют причины от 8 символов, серверного предпросмотра и отдельного применения. Несогласованные зависимости отвергаются, чтение не может иметь более узкую область, чем зависящее действие.

Глобальные изменения влияют на все организации, поэтому сохранение и предпросмотр требуют доступа ко всем действующим организациям. Профиль специалиста фиксирован: все зарегистрированные операционные права и никаких административных. При регистрации новых операций миграция должна дополнять этот профиль; произвольного создания permissions через UI нет. У администратора неизменяемо permissions.manage: его нельзя отозвать через API или изменение строки grant в БД. Это позволяет восстановить остальные права. При выдаче административных прав другой группе всем её пользователям сначала настраивается TOTP. Административная область — только «все» либо запрет.

Профиль ТСД по умолчанию ограничен тремя складскими сценариями. Расширение требует причины и ввода «РАСШИРИТЬ ТСД», показывается предупреждение об отклонении. Устройство само по себе прав не добавляет.

Сохранение атомарно увеличивает revision группы и auth_version её пользователей, удаляет их сессии, записывает diff и причину в неизменяемую историю. При следующем запросе прежняя cookie получает 401; оболочка проверяет сессию также при фокусе и каждые 30 секунд. Другие группы продолжают работать. Изменив собственную группу, администратор входит заново с новым кодом TOTP.

Проверка доступа пользователя — явно обозначенная симуляция permission, организации, владения и назначения. Она не подтверждает фактическое существование документа, его workflow, назначение либо MFA действующей сессии; окончательное решение остаётся за конкретным API. Список пользователей и его доступность дополнительно требуют users.manage; чужие организации недоступны.

## Бизнес-правила

31 параметр из BUSINESS-RULES.md: типы и диапазоны валидируются сервером без неявного превращения true в 1. Системное значение → переопределение организации → снимок подготовленной команды. Для глобальных значений нужен доступ ко всем организациям; переопределение доступно только в назначенных организациях.

Сброс восстанавливает наследование. Сохранение требует причины и предпросмотра. Ревизии системы и организации проверяются вместе: изменение системного значения после открытия формы вызывает 409 даже при сохранении переопределения. Два администратора не могут затереть изменения друг друга. История содержит старые/новые переопределения, автора, дату, причину и версию; страницы по 25 записей. UPDATE/DELETE/TRUNCATE истории запрещены триггером.

`policy.snapshot(connection, organization_id)` одним SQL-запросом получает согласованные значения и обе ревизии. Будущий сервис подготовки обязан сохранить возвращённый JSON вместе с payload; dispatch не должен заменять его новым чтением настроек. В этом срезе бизнес-документов и отправок ещё нет, поэтому изменение настроек не запускает операции, фоновые задания или внешние запросы.

Проверки количества, идемпотентность, резервирование, целостность КМ, обязательные внешние требования и подтверждённый успех не представлены выключателями. Три постоянных правила заблокированы. Политика исключения владельца, профили статусов, неподтверждённые профили принтеров и новые размеры этикетки пока также закрыты. Обязательные внутренние реквизиты логиста не разрешено уменьшать ниже supplier/number/date.

## Проверки

Unit: согласованность всех шести базовых профилей и зависимостей, типы/диапазоны каталога. PostgreSQL: авторизация и свежий MFA, изоляция организаций, preview без мутации, конкурентное сохранение, отзыв активной сессии, защищённые профили, версионирование и неизменяемая история, наследование/сброс и сохранность старого JSON-снимка. Chromium → Uvicorn → PostgreSQL: предпросмотр и применение прав, реальный выход сотрудника при отзыве, история, ошибки и сохранение правила, тёмная тема на 320 px. Ответы API не подменяются.
