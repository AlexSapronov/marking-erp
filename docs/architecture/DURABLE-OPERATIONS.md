# Очередь операций и серверный протокол подписанта

Миграция `0005_operations`. Этот инфраструктурный срез не содержит продуктивных HTTP-адаптеров, валидатора ГОСТ/CMS или Windows-агента. Контракты не регистрируются как подтверждённые автоматически; начальная очередь пуста. Эмиссия, СУЗ, НК и True API не вызываются. Успешные тесты транспорта не закрывают контрактный аудит и пилот CryptoPro/Рутокен.

## Подготовленная команда

Внутренний `operations.prepare` сохраняет точные bytes/SHA256, организацию, инициатора, тип/версию контракта, семантику read/mutation, текущую ревизию источника и полный снимок правил. `(organization,kind,idempotency_key)` уникален. Повтор того же намерения возвращает прежнюю операцию; другой payload/инициатор/источник/ревизия под тем же ключом даёт конфликт. Дополнительно уникален mutation по типу/источнику/ревизии: новый случайный ключ не позволяет повторить ту же команду. После изменения нужна новая ревизия источника. Смена настроек не переписывает сохранённый снимок. UPDATE исходной команды и DELETE/TRUNCATE запрещены в БД.

operation_targets и operation_assignments — внутренние связи текущей версии, владельца и назначения. Будущий бизнес-сервис обязан создавать/обновлять их атомарно со своим документом или заданием. Публичного создания произвольной операции/цели нет. Нельзя считать эти таблицы уже реализованной накладной или складским заданием. Подготовка неподтверждённого контракта сохраняет блокер.

## Обработка и восстановление

Claim использует PostgreSQL row lock/SKIP LOCKED, отдельный lease и возрастающий fence. Повторно проверяются действующий контракт, версия/остановка источника, enabled инициатора, организация, собственность/назначение и актуальные permissions с зависимостями. Для подписанной команды нужна проверенная подпись с действующим устройством и закреплённым сертификатом. Ключ lease хранится только как hash. Никакой транзакции или блокировки БД на время внешнего IO нет.

`dispatch_once` принимает явно зарегистрированные адаптеры `(kind,contract_version)`; в поставке их нет. Отсутствующий адаптер блокирует команду. Читающие операции допускают ограниченное число повторов, exponential backoff, jitter и ограниченный Retry-After. Семантика определяется контрактом, а не HTTP-методом: расходующий GET обязан быть mutation.

Timeout/обрыв или истёкший lease mutation переводит в unknown, без повторного claim. Это включает падение между фиксацией claim и фактическим HTTP: неоднозначность трактуется консервативно. Истёкший lease read допускает новую попытку с новым fence. Поздний ответ сохраняется как immutable evidence, но не применяется к новому состоянию. Транспортные исключения не сохраняются целиком, чтобы не записывать секреты из URL/сообщений.

Ответ отправки mutation может означать submitted, rejected или unknown; confirmed от этого шага не принимается. `reconcile` вызывается только доверенным читающим адаптером: проверяет fence, ожидаемые bytes hash, организацию и внешний ID. Его реализация должна доказать фактический состав/итог по контракту. Публичного endpoint установки статуса, подтверждения успеха или повторной отправки нет. Подтверждение внешнего факта не выполняет изменения будущего бизнес-документа: применение к его текущей версии должно быть отдельной проверяемой транзакцией.

История и raw квитанции append-only, raw не выдаётся обычному UI. Отмена до dispatch возможна внутренним сервисом; после dispatch она отвергается. Будущий бизнес-сервис обязан отдельно соблюдать подтверждение номера и остальные правила остановки.

## Подписант

Отдельная machine identity: bearer token хранится SHA256 в signer_devices, привязан к организации, allowlist подтверждённых типов и SHA256 сертификата DER. Обычная cookie, даже административная, не даёт доступа. Только POST `/api/signer/claim` и `/api/signer/result` освобождены от браузерных Origin/CSRF проверок; на них обязателен machine bearer. Все остальные изменяющие API сохраняют прежние проверки.

Claim возвращает job/operation ID, точный base64 payload, hash, тип/версию, целевую ревизию, сертификат, lease/fence/60 секунд. Одновременно у устройства только одна активная задача; попытки подписи и их lease сохраняются. Возврат связывается с конкретной выдачей, hash, сертификатом и nonce. Просроченный ответ сохраняется как свидетельство и не применяется; новую выдачу защищает новый fence. Устройство не получает команды ОС из payload.

Возврат CMS проверяет структуру DER и наличие закреплённого сертификата, но **не доказывает подпись**. Он переходит в received_unverified; operation остаётся awaiting_signature. `verify_received` без подключённого валидатора всегда отказывает. Только доверенный адаптер обязан проверить точные bytes, signer, цепочку/сроки/отзыв и допустимость сертификата для организации/операции; после этого можно поставить команду в очередь. Наличие сертификата в CMS не равно успешной криптографической проверке.

В тестах используется настоящий RSA CMS и OpenSSL с явно закреплённым синтетическим self-signed сертификатом, без проверки production-chain. Это подтверждает точные bytes и отрицательные случаи, но не ГОСТ, УКЭП, CryptoPro, драйвер токена, цепочку доверия ЧЗ или COM 32/64-bit. Эти проверки и запуск исходящего Windows user-agent остаются отдельным пилотом. Закрытый ключ и ПИН на VPS не передаются.

CLI после миграции:

```bash
# Только после регистрации проверенного контракта и подготовки валидатора.
marking-erp register-signer --organization-id UUID --name 'Рабочий подписант' \
  --certificate-sha256 SHA256_DER --kind APPROVED_KIND
marking-erp revoke-signer --device-id UUID
marking-erp recover-operations
```

Токен показывается один раз после commit; сохранить приватно, не помещать в Git/URL/логи. CLI требует доверенного доступа к БД, не является публичным setup. Без зарегистрированных approved signing contracts provision отвергается. Revoke блокирует новые выдачи/ответы и dispatch подписанных этим устройством команд. `recover-operations` восстанавливает только просроченные lease по указанным правилам; он не переотправляет mutation. Полноценный daemon/heartbeat-мониторинг обработчика будет подключаться вместе с первым проверенным адаптером.

## Интерфейс и проверки

`/operations` и GET `/api/operations`, `/api/operations/{id}`: SQL-фильтр по operations.view и own/assigned/all в разрешённых организациях. ТСД очередь недоступна. Показаны состояние, причина, версия источника/контракта, hash, история, metadata квитанций и непроверенная подпись. Полные payload/CMS/bearer/lease секреты в ответ не входят. История ограничена последними 100 записями, список имеет keyset pagination. Нет фиктивного успеха или кнопки «переотправить unknown».

PostgreSQL-тесты: идемпотентность, immutable intent/policy, два worker, crash/lease expiry, late fence, read retry, отзыв permission/пользователя и смена версии/остановка перед dispatch, receipt≠completion, привязка reconcile, отдельная авторизация подписанта, строгий CMS byte binding и неприменение старой подписи. Chromium → настоящий Uvicorn/PostgreSQL: unknown, история и отсутствие retry, светлая/тёмная тема, 320 px и запрет ТСД. Ответы UI API не подменяются; адаптеры в тестах синтетические и не обращаются к продуктивным системам.
