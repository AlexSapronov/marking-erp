# Транспорт чтения НК для изолированного пилота

25.10.2026. Следующий срез после офлайн-проверки PR10. Продуктивный адаптер,
web endpoint, фоновый worker и импорт карточек этим изменением не включаются.

Основание: [официальный API НК](https://docs.crpt.ru/gismt/API_НК/),
v5.68 от28.09.2026, разделы2,3.1.1,3.1.4; [таймауты HTTPX](https://www.python-httpx.org/advanced/timeouts/).
НК поддерживает Authorization: Bearer с токеном ГИС МТ как альтернативу apikey.
429 сообщает ограничение частоты, Retry-After задаёт ожидание в секундах;
API-Usage-Limit/API-Method-Usage-Limit сообщают счётчики запросов.

## Использование в коде пилота

`NkReadClient(environment=..., token=SecretStr(...))` создаётся явно в доверенном
процессе; конструктор не отправляет запросов. Среда обязательна: sandbox или production,
оба адреса закреплены в коде. Произвольные host/base_url не принимаются.
Получение/обновление токена не реализовано; API KEY из query string не поддерживается.
Не передавать токен через argv, URL, печать или публичные файлы.

`read_next(ReadPass(...))` читает одну страницу списка, проверяет её состав/пагинацию
и лишь затем получает детали по good_ids. При изменившемся total или повторном ID
детали не запрашиваются. При любом отказе исходный ReadPass не изменяется.
Успешный PageEvidence содержит новое состояние и исходные байты двух тел
(в пустой выборке детали не запрашиваются). Raw тела исключены из repr.
Их можно передать в приватный сборщик свидетельств; сам клиент ничего не сохраняет.
Сохраняются ограничения [проверки состава](../audit/NK-READ-CONTRACT.md):
bounded_pass не удостоверяет подлинность, атомарный snapshot, права организации или поля карточек.

Только GET /v4/product-list и GET /v3/feed-product. Универсального публичного request
или произвольных параметров нет; расходующие GET generate-gtins/feed-moderation исключены.
Секрет передаётся только в Authorization, ошибки содержат статические коды без
URL/ответа/текста сетевого исключения. Это не защита от отдельно включённого журналирования
полных HTTP-заголовков оператором; такой режим для реальных токенов недопустим.

## Проектная политика ограничений

- TLS проверяется; редиректы не выполняются, proxy/настройки из environment не наследуются.
- В одном клиенте пары запросов сериализованы, после каждого запроса пауза минимум2с.
  Это локальное ограничение экземпляра, не распределённая квота организации.
- Не более3 попыток одного GET при транспортном сбое или429/500/502/503/504.
  Backoff с jitter и Retry-After; автоматически ожидается не больше30с за одну паузу.
  Большая задержка возвращается как retry_after без сна/нового запроса, cooldown сохраняется.
 429 без корректного числового Retry-After даёт консервативную паузу300с.
- Исчерпанный общий или методный счётчик также блокирует экземпляр на300с.
  Нельзя обходить ограничение созданием нового экземпляра; до общего планировщика
  клиент применяется только в одном изолированном процессе пилота.
- 3xx/400/401/403/404/413 и остальные статусы не повторяются;413 не дробит время автоматически.
  Ошибки JSON/контракта/состава/формата тела также не повторяются.
- connect5с/read10с/write5с/pool5с; между полученными частями тела проверяется
  длительность попытки30с. Это не жёсткий wall-clock deadline: блокирующий I/O
  ограничивается соответствующим таймаутом, после него проверяется общее время.
- Только application/json и identity encoding, до8MiB на тело, проверка Content-Length
  и фактически полученных байтов. Поток закрывается и при ошибке; ошибка HTTP не требует чтения тела.

Бюджет попыток и cooldown живут в памяти; после перезапуска они не являются durable
состоянием. Для продуктивной очереди потребуются общий бюджет/квоты организации,
управление истечением токена, фиксированный контракт и операторский read-пилот.
Текущий клиент не зарегистрирован как адаптер очереди; контракты не активируются.

## Проверки

MockTransport проверяет точные URL/параметры и header авторизации, сохранность raw,
порядок список→детали, отсутствие продвижения при ошибке, bounded retry/cooldown,
ошибки прав, редиректы, квоты, медленный/большой/сжатый поток и закрытие ресурсов.
Логи HTTPX проверяются на отсутствие синтетического токена. Реальных сетевых
обращений, производственных ключей и подтверждения полного контракта в тестах нет.
