# Общие товары, КМ и файлы — первый срез

Миграция `0004_registry`. Этот срез не переносит бизнес-модули, не эмитирует КМ, не проверяет их криптографическую подлинность, не обращается к НК/СУЗ/True API и не запускает печать.

## Реестр

`/codes` — поиск по GTIN/КИ/PN, выбор разрешённой организации, страницы по 25, история версий, SHA256 и источники, скачивание разрешённых исходных байтов и уже сохранённых PDF. Пустая база показывает пустой реестр. ТСД не получает реестр. Количество AI30 относится к физической этикетке; это не подтверждённый остаток и не последнее количество ЧЗ.

GET `/api/codes?organization_id=...`, `/api/codes/{id}/history`, `/api/codes/{id}/payload/{payload_id}` проверяют codes.registry.view, codes.history.view и codes.payload.export соответственно. Списки фильтруются SQL по организации и own/assigned/all. Для own используется владелец записи доступа, для assigned — явная серверная связь code_assignments. Эти связи будут создаваться из документов/заданий соответствующими сервисами; назначать их через публичный API сейчас нельзя. Одного знания UUID недостаточно. Снятие permission проверяется при следующем запросе; оболочка обновляется при фокусе и каждые 30 секунд.

Исходный полный КМ не включается в списочные JSON или историю: скачивается отдельной бинарной командой с отдельным permission и аудитом. История показывает только метаданные и контрольные суммы. Файлы выдаются как attachment, с no-store и nosniff.

## Данные и происхождение

products — единая идентичность GTIN с checksum в Python и PostgreSQL. product_pns — неизменяемые PN/ТН ВЭД с организацией, типом подтверждённого источника, ссылкой и hash evidence. Регистр и символы PN сохраняются. Разные ТН ВЭД для GTIN не перезаписываются: внутренний register_product возвращает конфликт. Подготовка АТК обязана блокировать такой конфликт в будущем модуле. GET `/api/products` доступен по nk.cards.view в пределах организации и показывает provenance; это не синхронизация каталога.

codes идентифицируется `(product_group,cis)`, сравнение КИ учитывает регистр. payload версии изолированы организацией, immutable bytea: raw, normalized, два SHA256, профиль, преобразования, AI30, автор, источник и дата. Параллельное наблюдение одного КИ сериализовано advisory lock. Идентичный нормализованный payload — повторное наблюдение, другой — конфликт. Первый принятый payload остаётся базовым; конфликт не заменяет его, не меняет количество автоматически и не допускается к renderer. Между организациями не раскрываются чужие payload, PN, история или файлы. Nullable product_id допускает неизвестные сторонние КМ; их GTIN не превращается в выдуманную карточку. Последующее связывание товара будет отдельной версионируемой связью, а не UPDATE исходной записи.

Приём из подтверждённых внешних источников пока доступен только внутренним Python-функциям registry.py. Публичного создания/массового импорта КМ или товаров нет. Вызывающий будущий сервис отвечает за подтверждение источника и свои permissions; строка source сама по себе ничего не верифицирует. На UI нет фиктивной кнопки синхронизации или регистрации.

## GS1 и транспорт

Строгий профиль radio-strict-v1: 01 + GTIN14 + 21 + ИСН20, обязательные GS, шаблоны 36 (91/key4 + GS + 92/crypto44) и 37 (93/crypto4), необязательный конечный GS + AI30 (1..8 цифр, значение 1..99999999). Это ограниченный профиль радиоэлектроники, а не универсальный GS1 parser. Серийный номер и крипточасть не ищутся по подстрокам 30/91/92.

radio-scanner-v1 разрешает снять только начальный ]d2 и один завершающий CR/LF/CRLF, записывая причины. СУЗ-байты проходят исключительно строгий профиль. Потерянные GS, текстовые {GS}/^] и русская раскладка не исправляются догадкой: неоднозначный ввод отвергается, исходные данные у вызывающего сервиса остаются для разбора. Литеральные {GS}/^] внутри корректного serial сохраняются как обычные символы.

`division_entry` закрывает локальную регрессию S-004: source report содержит КИ + криптохвост без AI30, new report содержит AI30; между ними RS. Исходные байты не меняются. Это проверяемый транспортный helper, а не готовность всего контракта разделения/СУЗ или разрешение продуктивной отправки.

Источники, сверенные 25.10.2026: [форматы КМ ЦРПТ](https://docs.crpt.ru/gismt/Форматы_передаваемых_получаемых_КМ_КИ/), [GS1 DataMatrix Guideline §2.2](https://ref.gs1.org/guidelines/datamatrix/), [AI30 GS1](https://ref.gs1.org/ai/30). Сохранённые ограничения контрактного аудита остаются в TRUE-API-REVIEW.md и CHECKPOINT.md.

## Файлы и PDF

ERP_FILE_STORAGE_PATH по умолчанию `/var/lib/marking-erp/files`, вне webroot. Относительный путь и путь внутри публичного assets отвергаются конфигурацией. Сервису нужны права записи в этот каталог; каталог и файлы закрыты от других пользователей. В БД — случайный storage key, размер, тип и SHA256; клиентские пути не принимаются. Создание O_EXCL, файл 0600, проверка путей/симлинков и hash при каждом чтении. Составные FK связывают файл с конкретными code/payload/organization, metadata immutable. Повреждение/потеря файла даёт 503, содержимое и серверный путь не раскрываются.

save_payload_file сохраняет исходные байты. save_label рендерит только разрешённую версию и PN из подтверждённого источника той же организации, фиксируя PN, количество, шаблон и hash payload в snapshot. Нет публичного загрузчика произвольных PDF. Скачивание PDF требует marking.labels.download и доступа к соответствующему коду; это не складская перепечать из этапа17 и не подтверждение нанесения. Download не означает printed.

Renderer 58×40 адаптирован из аудированного marking-bm ce77a1cf. В начале DataMatrix — один FNC1 (232); внутренний ASCII GS кодируется как обычный байт (codeword30). Модули векторные, целое число точек при 203 dpi, размер label и quantity проверяются. Непомещающийся PN блокируется; кириллица требует серверного DejaVu Sans (`fonts-dejavu-core` на Ubuntu). Стандартный просмотрщик/драйвер должен печатать фактический размер; реальные S55/S45 и принтер ещё требуют отдельного пилота. Эталонный decode PDF не заменяет проверку на устройстве или в приложении ЧЗ.

Файловая запись предшествует фиксации БД: при rollback возможен недоступный через API файл-сирота. Автоматическая очистка пока не реализована; не удалять файлы по одному возрасту. Бэкап/восстановление должен включать БД и каталог файлов согласованно.

## Проверки

Строгий byte corpus: оба шаблона, GS/RS, AI-подстроки и спецсимволы serial/crypto, границы AI30, явный scanner transport, неизвестный/повреждённый формат, S-004. PDF реально рендерится в 203/300 dpi и декодируется ZXing-C++; сравниваются байты, ]d2, размеры и data codewords. PostgreSQL: checksum, provenance/PN/ТН ВЭД, конкурентные версии, неизменяемость, конфликт без перезаписи, own/assigned/all/org, прямые запрещённые скачивания, hash corruption и пагинация. Chromium работает с настоящим Uvicorn/PostgreSQL: реестр, конфликт, история, реальные загрузки .bin/PDF, поиск, 320 px и запрет ТСД. API не подменяется.
