# Личный вход и серверная авторизация

Реализованы личный вход, профиль и интерфейс управления учётными записями. Редактор групп и бизнес-модули пока не реализованы.
НК, СУЗ и True API этим кодом не вызываются. Все проверки permissions выполняются на сервере.

## Первая настройка

После миграций и seed из INFRASTRUCTURE-START.md:

```bash
# Создать ключ на доверенном компьютере; сохранить результат в защищённом окружении ERP.
.venv/bin/python -m marking_erp.cli generate-mfa-key
# Установить ERP_MFA_ENCRYPTION_KEY и ERP_PUBLIC_URL=https://<адрес ERP>.
.venv/bin/python -m marking_erp.cli bootstrap-admin \
  --username administrator --display-name 'Администратор' \
  --inn '<ИНН организации>' --organization-name '<Наименование организации>'
```

Пароль вводится скрыто дважды, не передаётся аргументом команды. CLI выдаёт новый ключ TOTP для ручного добавления
в приложение-аутентификатор и проверяет текущий код. Для первого входа нужен следующий код: использованный код повторно не принимается.
Ключ TOTP виден только при этой начальной процедуре; его нельзя публиковать или отправлять вместе с логами.
В БД секрет TOTP зашифрован Fernet; ключ шифрования хранится вне БД и Git и входит в защищённый комплект восстановления.
Замена ключа окружения без перешифрования ранее сохранённых секретов не выполняет ротацию автоматически.
Повторный bootstrap при наличии пользователей запрещён. Встроенного пароля или публичного HTTP-setup endpoint нет.

## Вход и сессия

- Логин нормализуется в ASCII lower-case. Пароль сохраняется как scrypt-v1 с индивидуальной случайной солью: N=131072,r=8,p=1.
- Сотруднику нужен пароль от12 символов; при создании административной учётной записи — от16 символов и TOTP.
- Для группы/permission административного класса вход без TOTP запрещён. Повторное использование временного счётчика блокируется в БД.
- Срок сессии сотрудника8часов, административной сессии30минут; административные действия требуют подтверждения за последние5минут.
- Cookie: Secure,HttpOnly,SameSite=Strict,Path=/, без Domain; имя __Host-erp_session. В БД только SHA256 случайного session token.
- Для локальной разработки допускаются ERP_PUBLIC_URL=http://127.0.0.1:8000 и ERP_SECURE_COOKIE=false; удалённый HTTP запрещён.
- Изменяющий запрос требует Origin=ERP_PUBLIC_URL и X-Requested-With=marking-erp; после входа также X-CSRF-Token из ответа/GET session.
- Ошибки валидации не возвращают входные значения пароля/секретов; ошибки БД не возвращают DSN и сообщения драйвера.

Пять неудач одной учётной записи либо50 одного IP за15минут блокируют дальнейшие попытки в соответствующем окне.
Счётчики живут в PostgreSQL и сериализованы advisory locks, не сбрасываются новым процессом.
Успешный вход очищает счётчик учётной записи, но не общий IP-счётчик.
За reverse proxy нужно явно доверять forwarded headers только адресу своего Nginx; произвольный X-Forwarded-For не является доверенным IP.

## API

| Метод | Путь | Назначение |
|---|---|---|
| POST | /api/session | username,password,otp; выдаёт cookie,csrf,user,permissions,organization_ids |
| GET | /api/session | Актуальное состояние текущего пользователя |
| DELETE | /api/session | Отзыв текущей сессии |
| POST | /api/session/logout-all | Отзыв всех собственных сессий |
| POST | /api/session/reauth | Повторное подтверждение пароля/нового TOTP |
| POST | /api/session/password | current password, new_password,otp; смена собственного пароля с выходом со всех устройств |
| GET/POST | /api/users | Просмотр/создание пользователей; users.manage и свежее MFA |
| GET | /api/users/options | Шесть групп и требование MFA; users.manage и свежее MFA |
| PATCH | /api/users/{id} | display_name,group_slug,enabled,organization_ids с обязательной auth_version |
| POST | /api/users/{id}/credentials | Сброс пароля/замена TOTP администратором, новая auth_version |
| POST | /api/users/{id}/revoke-sessions | Принудительный отзыв всех сессий пользователя |

При создании/замене TOTP через административный API нужны totp_secret и подтверждающий totp_code.
Пользователи API возвращаются только в пределах всех доступных администратору организаций; добавление чужой организации запрещено.
Последнего включённого администратора нельзя отключить или перевести в другую группу; у каждой ранее доступной ему организации также должен остаться администратор. Конкурентные изменения сериализуются.
Изменение группы, блокировка, сброс пароля или организаций увеличивает auth_version и отзывает сессии пользователя.
Изменение permissions группы проверяется без кеша при следующем запросе; сам редактор прав будет отдельным этапом.

## Применение к будущим бизнес-API

Actor.require проверяет permission, организацию, own/assigned/all и административный класс. Для операционного permission контекст организации обязателен.
owner_id и факт assigned должны поступать из серверной записи документа/задания, а не из JSON клиента.
Списочные запросы должны фильтровать данные в SQL; наличие permission.all не отменяет user_organizations.
Специалист не получает административные permissions; базовый профиль ТСД ограничен тремя складскими сценариями.
Dependency используется со scope=function: транзакция фиксируется до отправки успешного HTTP-ответа.

OIDC, привязка устройств ТСД, автоматическая очистка старых записей сессий и процедура аварийного
восстановления MFA пока не реализованы. Этот срез не является заявлением готовности ERP к корпоративному запуску.
