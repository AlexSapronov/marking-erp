# Согласованная копия PostgreSQL и файлов

Этот инфраструктурный этап закрывает проверяемость восстановления перед переносом бизнес-модулей. Продуктивные интеграции не включаются. Новая миграция не нужна: используется текущая схема `0005_operations`.

## Что сохраняется

`marking-erp-backup create --output /private/erp-backup.zip` создаёт новый файл 0600. Существующий файл не перезаписывается; публичный assets недопустим. В ZIP находятся custom pg_dump текущей ERP-схемы, все связанные записи files и исходные файлы по storage key, JSON-manifest с SHA256/размерами, версией схемы, временем завершения и build SHA. Случайные файлы-сироты и другие каталоги не включаются.

Отдельная REPEATABLE READ read-only транзакция экспортирует snapshot. Тот же snapshot передаётся pg_dump; список files читается из него. Включённые файлы уже записаны до commit и неизменяемы. Данные, добавленные после snapshot, не попадают ни в дамп, ни в список файлов. Перед фиксацией архива проверяются bytes/hash каждого файла; отсутствующий или повреждённый файл прерывает копирование без сохранения неполного ZIP. Общая advisory-блокировка исключает одновременную миграцию через штатную CLI, не блокируя обычные записи приложения.

Требуются pg_dump/pg_restore той же основной версии, что сервер; для PostgreSQL16 на Ubuntu — `postgresql-client-16`. При нескольких версиях выставить `ERP_PG_BIN_DIR=/usr/lib/postgresql/16/bin`. CLI по умолчанию сохраняет ERP-схему public, не весь кластер. Роли, tablespaces, пользовательские extensions/другие схемы и конфигурация системы не включены; текущая ERP не зависит от объектов вне своей схемы. Тестовая изолированная схема передаётся внутренним API явно.

Пароль БД не передаётся аргументом команды: только временный PGPASSFILE 0600 внутри приватного каталога. После процесса файл удаляется. stdout/stderr pg-tools не выводятся, чтобы не раскрыть credentials. Поддержаны sslmode/sslrootcert/sslcert/sslkey/connect_timeout из URL; неизвестный параметр отвергается, а не теряется молча. Поддержаны обычные имена БД без libpq connection-string синтаксиса.

Копия содержит чувствительные данные БД и полный КМ; ZIP **не зашифрован**. Хранить в закрытом зашифрованном резервном хранилище с доступом ИТ, не в webroot, общих папках или Git. Ключ ERP_MFA_ENCRYPTION_KEY хранится отдельно в защищённом комплекте восстановления; в manifest только его SHA256. Без исходного ключа восстановление данных с TOTP отвергается. Secret env/сертификаты/TLS/config/systemd сохраняются отдельной процедурой ИТ.

## Проверка без БД

```bash
marking-erp-backup verify --bundle /private/erp-backup.zip
```

Проверяются структура, версия, CRC/размеры/SHA256, заголовок custom dump, список и имена файлов. Нет extractall: посторонние пути, symlinks, дубликаты и неожиданные ZIP-members отвергаются. Эта команда не исполняет SQL и не доказывает восстановимость PostgreSQL; это проверяется реальным restore. Manifest с hash обнаруживает повреждение, но не подтверждает подлинность недоверенного архива. Восстанавливать только собственные доверенные копии: pg_restore исполняет SQL исходного владельца.

## Восстановление в новую БД

Сохранить исходный MFA-ключ в ERP_MFA_ENCRYPTION_KEY и отдельно задать `ERP_RESTORE_ADMIN_URL` на служебную БД, например postgres, с правом CREATE DATABASE. URL не передаётся аргументом shell и не выводится. ERP_DATABASE_URL остаётся настройкой исходной/runtime среды; restore подключается через отдельный admin URL.

```bash
marking-erp-backup restore --bundle /private/erp-backup.zip \
  --new-database erp_restore_20261025 \
  --files-path /var/lib/marking-erp/restored-files-20261025
```

Имя БД и каталог обязаны быть новыми. Никакая существующая БД/папка не очищается. CREATE DATABASE должен успешно создать новый объект прежде, чем pg_restore получит --clean; --create из архива не используется. Restore идёт одной транзакцией с exit-on-error в только что созданную БД. При ошибке удаляются только БД/каталог, созданные этим запуском; если автоматическая очистка не удалась, остаётся изолированная незавершённая копия для разбора. Исходная среда не изменяется.

После restore metadata files сверяется с manifest и проверяются фактические файлы. Только затем:

- Удаляются восстановленные сессии и повышается auth_version пользователей; нужен новый вход.
- Повторное использование текущего TOTP-счётчика запрещается; администратору нужен следующий код.
- Устройства подписанта выключаются, задания подписи отменяются с сохранением evidence.
- Все подтверждения operation_contracts снимаются.
- Активные отправки переводятся в unknown с новым fence, готовящиеся команды блокируются. Submitted и неизвестные результаты сохраняются для сверки. Терминальные подтверждённые факты не переписываются.
- В audit появляется system.restored с hash архива и отметкой выключенного dispatch.

Копия остаётся изолированной: приложение/worker не переключаются автоматически, интеграции не включаются. Перед переключением ИТ должен сверить внешние действия со времени snapshot (включая операции, отсутствующие в старой копии), подтвердить данные/файлы, перенастроить доступы и только затем отдельно разрешать подключения. Новый случайный idempotency key не является способом повторить старую неизвестную операцию. RPO/RTO этим тестом не гарантируются; расписание и offsite/retention определяются ИТ.

Ограничения v1: один schema, до100000 файлов по10MiB, custom dump до128GiB, manifest до64MiB, стандартный timeout pg-tools900с. Более крупная база и PITR/physical backup требуют отдельной политики ИТ. Запуск отдельной копии не равен успешному производственному переключению.

## Проверки

CI использует PostgreSQL16 и реальные pg_dump/pg_restore. Проверяются исходные .bin/PDF после восстановления и вход новым паролем/сессией; прежняя cookie не работает, очередь не отправляется, исходная БД остаётся прежней. Параллельная запись во время dump доказывает согласованность экспортированного snapshot и files. Есть отрицательные тесты отсутствующего файла, неверного MFA-ключа, существующей БД/папки, повреждённого архива и traversal. Команды PostgreSQL в этих тестах не подменяются.

Основа реализации: официальная документация PostgreSQL16 [pg_dump](https://www.postgresql.org/docs/16/app-pgdump.html) и [pg_restore](https://www.postgresql.org/docs/16/app-pgrestore.html). Отдельно сохраняются ограничение --schema и риск исполнения недоверенного SQL.
