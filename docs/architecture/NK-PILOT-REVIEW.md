не использует токен, не подключается к БД и не импортирует карточки в ERP.

```bash
marking-erp-nk-review \
  --capture /var/lib/marking-erp/nk-pilots/pilot-001 \
  --output /var/lib/marking-erp/nk-reviews/review-001
```

Вход — остановленный [пилот PR12](NK-PILOT-CAPTURE.md) с run.json, manifest.json и raw телами.
Родитель выходной папки уже должен существовать. Выход создаётся новым, вне проекта/пакета:
папка0700, файлы0600, без symlink/повторного использования существующего каталога.
review.html можно открыть локально в браузере; review.json содержит те же кандидаты
и стабильные коды замечаний. Не публиковать эти файлы: в них есть данные каталога.
stdout содержит только счётчики и коды, без PN/GTIN/содержимого карточек.

## Проверка свидетельств

Для каждого receipt run.json проверяются имя, уникальность, формат SHA256, размер,
UTC/offset timestamp и тождество исходного тела. Сверяются также неподтверждённые
последние HTTP200, но они не превращаются в карточки. Каждая ссылка manifest должна
иметь receipt; изменённое, отсутствующее или подменённое тело останавливает разбор.
Бюджет чтения — до800 receipts/256MiB тел; один файл до8MiB.

Затем существующий checker проверяет пагинацию и состав деталей. Разбор получает
именно проверенные байты и повторно сверяет их hash с receipt перед проекцией полей.
Тела с неверным JSON вне manifest остаются только свидетельствами: они не разбираются
как карточки. Неизвестные файлы отмечаются счётчиком и не читаются.
Неполный обход, незавершённый запуск, расхождение checkpoint и ответы вне manifest
попадают в замечания. После аварии эти расхождения могут быть закономерны; автоматического
восстановления, удаления или склеивания запусков нет.

Флаг receipt_hashes_match означает локальное совпадение файлов с переданными receipts.
Изменивший и тело, и receipt может получить согласованный набор. Run hash фиксирует
прочитанную версию metadata, но не удостоверяет источник, время, окружение или аккаунт НК.
Отчёт не является tamper-proof доказательством или атомарным snapshot каталога.

## Проектная диагностика карточек

Это предварительные правила просмотра, не полный валидатор официального API:

- Кандидат PN берётся только из attr_id13914. Выбор опирается на аудированный исходник
  nk-manager SHA06f420f38b9ac100bd568f1238034fb1e601791d, не на закрытый продуктивный контракт.
  Названия атрибутов, бренд и похожие строки не используются как fallback.
  Несколько различных PN не сводятся к одному; совпадение с брендом отмечается.
- GTIN: только type=gtin/level=trade-unit, строка из14 ASCII-цифр с верной контрольной цифрой;
  multiplier должен быть целым1. Числа/короткие коды не дополняются нулями, упаковочный
  GTIN не становится GTIN единицы. Иные допустимые идентификаторы НК не объявляются нарушением API:
  для текущего кандидата ERP их недостаточно.
- Полный ТН ВЭД:10 цифр из tnved или attr_id13933 (также гипотеза аудированного источника).
  Противоречия и несовпадающая краткая группа отмечаются; классификация по ФТС не подтверждается.
- Неизвестный/нетекстовый статус и неверный тип good_signed отмечаются. Заявленная публикация
  без true-флага подписи требует разбора. Никакой статус не становится подтверждённым статусом ERP.
- Дубли PN ищутся по strip+casefold только как предупреждение; оригинальные значения сохраняются.
  Дубли GTIN также предупреждаются. Локальные кандидаты с неоднозначностями не объединяются.
  Похожие PN/транслитерация/конфузаблы не анализируются.
- Значения-кандидаты ограничены256 символами. Длинные или нетекстовые значения не угадываются.
  Известные поля проецируются явно; остальные raw поля, URL и изображения в отчёт не копируются.

HTML экранирует значения и запрещает скрипты/внешние ресурсы через CSP; JavaScript нет.
JSON сохраняет исходные строки кандидатов. Поля contract_verified/import_allowed,
authenticity_verified/erp_imported всегда false даже при нуле замечаний.

Коды завершения:0 — разбор завершён без замечаний (не разрешение импорта);
2 — отчёт создан с замечаниями или неполным охватом;1 — ошибка целостности/формата/записи.
При ошибке входа выходной каталог не создаётся. Исходные файлы не изменяются.

## Проверки реализации

Синтетические регрессии: подмена корректного JSON при старом hash, missing/duplicate receipt,
неверные пути/размеры/время, pending ответы, checkpoint drift, PN без fallback/неоднозначность,
GTIN/ТН ВЭД/статусы, дубли, экранирование HTML и приватные коды выхода CLI.
Успешный разбор синтетики не закрывает полный контракт, I-001 и CHECKPOINT.
